# guest/ — Contract Findings & Notes

Running log of observations about the IndbyAgent invite contract that shape the CLI implementation.

## Contract findings

### 1. Actions are "METHOD URL" strings, not objects
`src/lib/invite.ts:73-79` — Each action value is a string like `"POST http://host/i/TOKEN/rsvp"`.
The CLI parses these by splitting on the first space. If no space is present, it defaults to GET.

### 2. Schema is prose, not JSON Schema
`src/lib/invite.ts:80-85` — The `schema` block uses human-readable notation (e.g.
`"yes|no|maybe|needs_human"`, `"int<=1"`, `"same"`). It is descriptive, not machine-parseable.

### 3. Schema lists actions not always offered
`src/lib/invite.ts:80-85` — `schema` always includes `rank_poll`, `answer_poll`, and
`message_host`, even when those actions are absent from `actions` (e.g. `rank_poll` only appears
in `actions` when there are date polls). An agent should check `actions`, not `schema`, to know
what's available.

### 4. The strip() function removes null, empty string, and empty arrays
`src/lib/invite.ts:41` — `Object.fromEntries(Object.entries(o).filter(([, v]) => v != null && v !== "" && !(Array.isArray(v) && v.length === 0)))`.
This means any field can be absent. The CLI must treat every field as optional except
the known-always-present ones.

### 5. Fields guaranteed present (by reading inviteJson)
- `indbyagent` — always the SPEC_VERSION constant
- `party.title` — from Party.title (non-null in DB type)
- `party.timezone` — from Party.timezone (non-null in DB type, but strip() applies)
- `guest.name` — from Guest.name (not stripped, always set)
- `guest.party_size_max` — from Guest.party_size_max (numeric, always set)
- `rsvp.status` — defaults to "pending" (`state.status ?? "pending"`, line 56)
- `actions.rsvp` — always present (line 74)
- `schema` — always present (lines 80-85)

### 6. party.timezone vs. absent
`src/lib/db.ts:22` — `timezone: string` (non-null in the Party type). However, strip()
could theoretically remove it if it were empty string. In practice the server always sets it.
The CLI falls back to UTC if missing.

### 7. rsvp.status can be "pending"
`src/lib/invite.ts:56` — `status: state.status ?? "pending"`. The RsvpStatus type includes
`"pending"` (`src/lib/db.ts:16`). This is the initial state before the guest or agent responds.

### 8. Action URLs use the server's siteUrl(), not the request origin
`src/lib/invite.ts:40` — `const base = \`\${siteUrl()}/i/\${token}\``. The `siteUrl()` function
reads `NEXT_PUBLIC_SITE_URL` / `VERCEL_URL` env vars (`src/lib/token.ts:19-24`). In development
this defaults to `http://localhost:3000`. If a user fetches from `http://127.0.0.1:3000`, the
action URLs will say `http://localhost:3000` — a cross-origin mismatch. The CLI warns about this.

### 9. Token shape: 20-40 chars of base64url alphabet
`src/lib/token.ts:11-12` — `/^[A-Za-z0-9_-]{20,40}$/`. Generated by `randomBytes(20).toString("base64url")` which produces ~27 chars. The CLI reimplements this regex.

### 10. polls array shape
`src/lib/invite.ts:67-71` and `src/lib/db.ts:34-35`:
- Poll fields in JSON: `id`, `kind` ("preference"|"dates"), `q` (question), `options` (string[]),
  `timezone` (only on dates polls), `closes_at` (optional), `your_answer` (preference only),
  `your_ranking` (dates only). All go through strip().
- DB Poll type has `status` and `party_id`, but these are not serialised to the invite JSON.

### 11. polls_after_yes
`src/lib/invite.ts:64` — When there are open preference polls but the guest hasn't said yes,
`polls_after_yes` is a count of the locked polls. The CLI displays this note.

### 12. hint field
`src/lib/invite.ts:86` — Present only when there are date polls and no starts_at. Contains a
human-readable instruction about ranking dates.

### 13. Error responses
`src/lib/http.ts:5` — 404 returns `{ error: "not found" }`.
`src/lib/http.ts:18-20` — 400 returns `{ error: "invalid", issues: [...] }`.
The CLI prints the `error` field verbatim.

### 14. party.date = "tbd"
`src/lib/invite.ts:63` — When `starts_at` is null, the JSON includes `party.date = "tbd"`.
This is a synthetic field not in the DB Party type.

### 15. needs_human status offered in schema but restricted in CLI
`src/lib/invite.ts:81` (`schema.rsvp.status: "yes|no|maybe|needs_human"`) and `src/lib/invite.ts:161` (`z.enum(["yes", "no", "maybe", "needs_human"])`).
The server accepts `needs_human` (meaning an agent is consulting its human before answering). The CLI restricts user-provided `--status` to `yes|no|maybe`.

### 16. Idempotency-Key header handling & unique constraint 23505
`src/lib/http.ts:31-33` (`idem(req): req.headers.get("idempotency-key")`) reads the header verbatim with no length or charset restriction in code.
`supabase/migrations/20261004171052_indbyagent_core.sql:60` (`create unique index rsvps_idem_idx on rsvps(guest_id, idempotency_key) where idempotency_key is not null`).
`src/lib/invite.ts:176-182`: `writeRsvp` catches Postgres error code `23505` and treats it as success (`return { ok: true }`). It does not update the row or flag the replay.
Because `respondWithInvite` returns the latest row from `guest_state`, a replayed key with a different body silently leaves the original RSVP intact.

### 17. Server party_size defaulting and validation
`src/lib/invite.ts:174-175`: `const size = body.party_size ?? (body.status === "yes" ? 1 : 0); if (size > ctx.guest.party_size_max) return { error: \`party_size exceeds max of \${ctx.guest.party_size_max}\` };`.
When omitted, `party_size` defaults on the server to 1 for "yes" and 0 for other statuses. If it exceeds `party_size_max`, the server returns a 400 error JSON: `{"error": "party_size exceeds max of N"}`.

### 18. Browser form vs API in RSVP route
`src/app/i/[token]/rsvp/route.ts:13-24`: If `content-type` includes `form`, it parses multipart form data, defaults `by.kind` to `human`, channel to `web`, and redirects 303. Otherwise it parses JSON via `parseBody(req, RsvpBody)` (`src/lib/http.ts:14-23`), sets channel `api`, defaultKind `agent`, and responds with the updated invite JSON.
